## 存储所有权的恢复边界（2026-10-24）

机器启动时间的秒级估算不能证明原写入者已退出。本机真实子进程已出现原进程存活、两边启动估算相差一秒的情况。现在必须先确认原 PID 不存在才可回收；PID 仍在且身份不同，或无法确定是否存活，均保留原租约并拒绝写入，也不会据此调用模型。

死进程租约回收复用现有 `StoreLease` 创建短暂的 `lease.reclaim` 守卫；取得守卫后重新核对当前所有者，避免两个进程都读到旧记录后，后到者删除先到者的新租约。守卫不自动回收自身：若恰在回收临界区退出，守卫残留、缺少完整所有者或无法确认身份时，后续保持占用状态，要求人工核对。此限制保留原数据，不承诺所有异常都能自动恢复，也没有新增自动删锁入口。

释放路径没有增加第二套调度：`DurableStoreHandle.close()` 在首次等待前同步设置关闭标记，因此同一 handle 只释放一次；打开失败的释放分支互斥；会话元数据更新和回收守卫各只有一个 `finally` 释放，并继续核对原 token。相邻模块回归覆盖启动估算漂移、死进程回收、过期读取与新所有者竞争、残留守卫以及错误 token 不删除他人守卫；真实 SDK 子进程回归另核对跨进程拒绝写入和崩溃后明确继续。
